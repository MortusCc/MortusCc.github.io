三个实验，三段进化：从裸奔代码到软件构造的工程化思维

三个实验，三段进化：从裸奔代码到软件构造的工程化思维

写在前面

学期初，我拿到一个 FastAPI 后端项目。它能跑，但浑身是病。

学期末，它活了——有测试安全网、有抽象分层、有策略调度。

这不是魔法。这是三个实验教会我的事。

实验一：让项目”活”过来

依赖地狱与 Poetry 救赎

项目最初的依赖管理方式是 requirements.txt。你猜怎么着——它缺包。

缺到 python run.py 根本起不来。ModuleNotFoundError 一个接一个，像打地鼠。

这就是传统 requirements.txt 的痛点：没有版本锁定、不区分开发依赖和生产依赖、手工维护容易遗漏。

Poetry 解决了这一切：

pyproject.toml + poetry.lock = 环境可复现。任何人拿到项目，两条命令就能跑起来。

写测试前，先看懂代码

实验要求为 app/utils/ 下的工具函数写单元测试。我在 AI 的帮助下，555 个测试用例全部通过，app/utils 覆盖率达到 100%。

但关键不是数字，是策略：

策略 说明
Happy Path 正常输入得预期输出
Unhappy Path 空输入、越界、异常输入
分支覆盖 if/else、异常捕获、early-return 逐条覆盖
依赖隔离 用 Mock/Monkeypatch 去掉 DB、网络、文件系统

测试反哺代码——我修了三个真问题

写测试不是为了交作业，它真的能反哺代码质量。我在补齐覆盖率的过程中发现了三个真实问题：

  1. 资源泄漏：analyze_image_with_model 在早返回路径下数据库会话未关闭。修法——用 finally 兜底。
  2. 不可测试代码：图片分析结果注入逻辑嵌在长流程里无法单测。修法——抽取纯函数 _inject_image_analyses_into_markdown。
  3. 测试依赖网络：远程 MinerU 解析路径默认优先，本地测试根本覆盖不到。修法——新增 MINERU_REMOTE_ENABLED 环境变量开关。

教训：不可测试的代码，往往也是设计有问题的代码。

代码坏味道第一课

翻源码时我发现的几类典型问题：

  • 注释坟场：大段注释掉的旧逻辑还挂在主干上。Git 才是历史记录该待的地方。
  • print() 调试残留：日志不该靠 print，该用结构化日志（logger）。
  • 裸 except: pass：吞掉异常等于埋地雷，炸了都不知道。
  • 重复逻辑：提取 JSON 的逻辑在两个文件里各写一遍。抽公共函数！

实验二：面向接口编程 vs 裸数据结构

新增一个 Model Provider，不改一行主逻辑

实验要求新增一个大模型服务商。我选了 DeepSeek。

关键是——我只写了一个新文件 deepseek_provider.py，继承 ModelProvider 抽象基类，实现 chat_completion、text_completion、embedding 三个契约方法。

主流程代码一行没改。Provider 管理器自动扫描加载。重启服务就能用。

这就是开闭原则：对扩展开放，对修改关闭。

如果每加一个 Provider 都要去主流程里加 if-else，说明架构违反了 OCP。

SessionContext：给裸数据穿上防弹衣

聊天链路里，final_messages 是一个普通的 List[Dict]，在七八个步骤之间穿梭。任何一个环节手滑 append 或改键，下游就炸。

这就像把现金塞在透明塑料袋里满街跑——太危险了。

我设计了 SessionContext 作为 ADT：

  • AF（抽象函数）：表示一次对话的消息上下文
  • RI（表示不变量）：每条消息必须有 role 和 content，role 只能取 system/user/assistant，总数不超过 50
  • 防御性编程：
    • 写入时深拷贝 + 校验
    • 导出时返回深拷贝（外部修改不污染内部）
    • 每次状态变更后自动 _check_rep()

然后写”破坏性测试”证明：传非法 role → 抛异常；拿到 to_list() 返回值后修改 → 内部状态不变。

这是实验二给我的最大启发：数据结构不是数据 + 注释，而是数据 + 规则 + 防御。

踩坑记录

端到端验证时碰到一堆环境问题：Swagger OAuth2 的 tokenUrl 配错了、路由匹配顺序导致接口被错误命中、流式/非流式返回类型不一致导致 async for 炸了。

这些全是”代码能跑但环境不通”的问题。教训：真实工程中，先确认主路径通不通，再开始写代码。

实验三：把上帝函数送上手术台

先量体温，再开刀

实验三的目标函数是 chat_with_agent。它有八大职责：

  1. 请求解析与访问控制
  2. 文件上下文处理
  3. 联网搜索
  4. 知识库向量检索
  5. 知识图谱检索
  6. MCP 服务调用
  7. 消息装配与推理
  8. 聊天历史写库

全塞在一个路由函数里。这就是上帝函数——什么都干，什么都干不好。

结果：Complexity 等级 C/D，分数高得吓人。这成了我的重构基线。

砍一块，验一块，再砍下一块

重构原则：小步替换，持续验证。每一刀下去保证行为不变。

第一刀：清理垃圾

  • 删掉未引用的 import
  • 删掉注释掉的旧版路由实现
  • 删掉死代码
  • print() 换成日志（或直接删）
  • time.sleep() 换成 await asyncio.sleep()（异步事件流里同步阻塞 = 性能炸弹）

第二刀：服务下沉

把神函数里的四大块逻辑拆成独立服务：

服务 职责
DocumentContextService 按 file_ids 查库/读 MinIO/抽取文本/截断
KnowledgeRetrievalService embedding + 向量库召回 + 结果格式化
GraphRetrievalService LLM 生成 Cypher + Neo4j 查询 + 可视化
AgentChatService 统一编排”构建上下文 → 增强 → 推理 → 写库”

主函数退化为”编排者”：鉴权 → 分流 → 调 service → 返回。

手术效果

重构后再跑 Radon：

  • chat_with_agent：Complexity 等级 A，分数从巨高降到 3
  • 全文件平均复杂度：A（2.86）
  • 全量测试：578 passed

从”谁都不敢碰”到”谁都能看懂”。

AI 辅助编程：我的使用原则

三个实验全程用了 AI，但有一条铁律：

理解在前，生成在后。

先用自己脑子读懂代码——输入输出是什么、异常约定是什么、外部依赖有哪些。再把代码丢给 AI 生成草稿。最后人工校验：断言合理吗？分支覆盖全吗？引入了不稳定依赖吗？

AI 是加速器，不是替代品。你不理解代码，AI 写错了你也看不出来。

三个实验，三层递进

这恰好是一个真实软件工程项目的进化轨迹：

  1. 质量兜底（测试 + 覆盖率）
  2. 抽象分层（OOP + ADT + 契约）
  3. 结构优化（重构 + 设计模式 + 复杂度度量）

十条经验

  1. 让项目先跑起来。读 README、搭环境、跑通主路径——这是接手任何项目的第零步。
  2. 用 Poetry 管依赖。别再用裸 requirements.txt 自虐了。
  3. 测试不是负担，是安全网。写得好的测试让你改代码时有底气。
  4. 覆盖率 100% ≠ 测试好。覆盖关键分支和错误路径才有意义。
  5. 不可测试的代码 = 设计有问题的代码。为了可测试性重构，往往能发现更好的结构。
  6. 封装不是把数据塞进类里。AF + RI + 防御性编程才是真正的抽象。
  7. 开闭原则不是背概念。新增一个 Provider 不改主流程一行代码——这就是活生生的 OCP。
  8. 先量化再重构。Radon 跑一下，记下基线，改完再跑——重构收益可度量。
  9. 小步改，持续验。砍一块就跑测试，比一次爆改全炸了强一万倍。
  10. AI 是你的副驾驶。但你得先会开车。

结语

这三个实验不是”写代码”，是”修代码”。

拿到一个浑身毛病的项目，一步步让它变得干净、可测、可扩展——这个过程比从零写新项目难得多，也学到多得多。

软件构造的本质，不是让代码跑起来，是让代码能被人维护下去。
